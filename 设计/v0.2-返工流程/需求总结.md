# 返工流程 — 需求总结

> 版本：v0.2
> 日期：2026-08-07
> 状态：设计稿已产出，待用户交互确认

---

## 背景

任务处于“审核中”（产品语义为交付验收）时，用户或 AI 可能发现需要修改的问题。当前“提交修改意见并返工”会把任务直接移动到开发中并启动 Luna，导致返工范围没有经过开发前审核，也使 AI 复核意见无法稳定成为返工输入。

用户确认采用方案 A：返工意见先生成一轮返工单，任务回到待开发；Sol 只读审核本轮返工范围，通过后才进入开发中。

## 目标

本版本要解决的核心问题：

1. 返工意见不能再绕过 readiness 直接启动开发。
2. 用户意见和 AI 复核意见使用同一条返工入口、同一份结构化返工单和同一套审核规则。
3. 看板和任务详情能识别当前是否属于返工，以及处于第几轮返工。
4. 返工范围信息不足、审核失败或启动失败时，系统显示真实状态并允许继续处理，不能进入半完成状态。
5. 保留每轮返工的来源、汇总、审核结论和验收结果，形成可追溯经历。

## 功能范围

### 做什么

- 在交付验收阶段提供“提交返工并重新审核”动作。
- 用户提交修改意见时生成“第 N 轮返工单”，任务回到待开发并启动 Sol 返工范围审核。
- AI 交付复核发现问题后展示结构化结论和“采纳意见并发起返工”动作。
- 用户入口和 AI 入口调用同一个服务端返工命令，产生相同的状态与审核后果。
- 返工单保存本轮来源、汇总、关联评论、修改范围、通过标准、轮次和当前结论。
- Sol 同时读取任务上下文、当前交付和本轮返工单，不再只依赖用户评论列表。
- Sol 返回 `needs_confirmation` 时进入待解决；用户补充后继续同一轮返工审核。
- Sol 返回 `ready` 时自动进入开发中，并创建或恢复 Luna 开发对话。
- 看板卡片和任务详情显示小标识 `↩ 返工 #N`。
- 返工重新交付后继续显示标识；用户接受交付后从活动卡片隐藏，历史仍保留。
- 覆盖原子写入失败、版本冲突、Sol 启动失败、部分信息不可用、重复点击、归档只读、多轮返工、长文本、移动端和深色主题。
- 提供准确的成功、警告、错误 Toast，以及完整交互行为规则表。

### 不做什么

- 不新增“待返工”或“返工中”任务状态（原因：待开发、待解决、开发中和交付验收已经能表达真实执行阶段）。
- 不允许普通 AI 评论自动改变任务状态（原因：建议与正式返工是两种不同业务动作，必须有明确触发）。
- 不允许返工操作直接启动 Luna（原因：必须先经过 Sol 返工范围审核）。
- 不重做整个任务详情、看板或评论系统（原因：本版本只补充返工闭环及其必要展示）。
- 不把所有历史 Agent 评论自动拼接为返工范围（原因：容易引入旧结论、讨论内容和无关反馈）。
- 不在本设计阶段确定最终数据库表结构或迁移脚本（原因：设计只规定必须持久化的数据和原子行为，工程实现另行评审）。
- 不在本轮修改产品代码、状态枚举、服务端业务规则或测试（原因：当前交付物是 PRD 前设计参考）。

## 载体

现有 Dashi Taskboard 应用：

- 主入口：任务详情页交付验收区和评论输入区。
- AI 入口：Sol 交付重新审核结果卡片。
- 轻量展示：看板任务卡片、任务详情标题区和当前阶段卡。
- 历史展示：任务经历记录中的返工单、审核轮次和验收结果。

视觉沿用当前 Taskboard 的 Linear 风格、浅色/深色主题变量、任务详情双栏布局和既有按钮层级；同时继承 `设计/v0.1-任务状态流程/` 对阶段名称和状态展示的约定。

## 核心流程

```text
交付验收 in_review
  → 用户提交返工意见 / 采纳 AI 返工建议
  → 原子生成第 N 轮返工单
  → 待开发 todo + ↩ 返工 #N
  → Sol 只读返工范围审核
      ├─ needs_confirmation → 待解决 blocked → 补充 → 继续同一轮审核
      └─ ready → 开发中 in_progress → Luna 执行
  → 交付验收 in_review + ↩ 返工 #N
      ├─ 接受交付 → 待复盘，活动标识隐藏、历史保留
      └─ 仍有问题 → 创建第 N+1 轮返工单
```

## 关键决策

探索过程中确认的产品和设计决策，PRD 和开发阶段必须遵守：

| # | 决策 | 原因 |
|---|------|------|
| 1 | 采用方案 A：交付验收 → 待开发/返工审核 → 开发中 | 用户已明确选择并确认；符合现有 readiness 门禁 |
| 2 | 返工不是新的任务状态 | 避免状态膨胀，继续使用真实执行阶段表达任务位置 |
| 3 | 使用 `↩ 返工 #N` 作为统一小标识 | 一眼区分首次开发和第 N 轮返工，同时不取代状态 |
| 4 | `in_review` 的用户界面名称使用“交付验收” | 与开发前的需求审核、返工范围审核明确区分 |
| 5 | `todo + active rework + readiness running` 显示为“返工审核中” | 向用户展示真实经历，而不是只显示宽泛的待开发 |
| 6 | 用户意见和 AI 复核意见统一冻结成返工单 | 让审核输入稳定、可追溯且不依赖评论作者类型 |
| 7 | AI 复核结论默认只生成建议，需明确点击“采纳意见并发起返工” | 防止普通 AI 评论或误判自动改变任务状态 |
| 8 | 发起返工是一个服务端原子命令 | 避免评论已保存但状态未移动，或状态已移动但 Sol 未触发的半完成状态 |
| 9 | 发起返工本身绝不创建或启动 Luna | Luna 只能由 Sol `ready` 结论后的服务器路径启动 |
| 10 | 信息不足进入待解决，但保持当前返工轮次 | 用户补充属于同一修改请求，不应虚增轮次 |
| 11 | 原评论编辑不静默修改已冻结的返工单 | 保证 Sol 审核输入与历史证据稳定；更新范围需要显式重新审核 |
| 12 | 接受交付后活动卡片隐藏返工标识，历史记录保留 | 减少已结束任务的视觉噪声，同时保留追溯能力 |
| 13 | 同一幂等请求不得创建多个返工轮次或并行 Sol | 防止重复点击和网络重试造成重复开发 |
| 14 | 版本冲突时刷新状态并保留草稿，不自动重放 | 避免任务已被接受或取消后，旧请求仍把它拉回待开发 |

## 返工单信息结构

设计要求持久化以下业务信息，具体数据库结构由工程阶段决定：

| 字段 | 用途 |
|---|---|
| 任务与轮次 | 唯一定位 `task + rework round`，驱动 `↩ 返工 #N` |
| 发起来源 | 区分用户修改意见、AI 交付复核或具备权限的 Agent 动作 |
| 返工汇总 | 本轮唯一、冻结的修改范围描述 |
| 来源引用 | 关联用户评论、AI 复核评论、附件和交付说明 |
| 通过标准 | Sol 判断是否足以开始开发以及后续用户验收的依据 |
| 审核关联 | 当前 readiness review、AI thread/run、审核结论和 Q 编号问题 |
| 生命周期时间 | 发起、审核通过、重新交付、接受或取消时间 |

返工单是本轮审核的明确输入。它不能通过“读取所有 Agent 评论”动态重建，也不能因来源评论后来被编辑而静默变化。

## 技术约束

- 当前直接返工逻辑位于 `web/src/components/TaskDetail.tsx`：先写 `status: in_progress`，再创建任务绑定 AI 对话并启动开发。实现时应删除这条前端直启路径，改为调用单一服务端返工命令。
- 当前评论动作类型为 `comment | review | development | discussion`。返工不再等价于 `development`；工程实现需要增加明确的 `rework` 业务语义，或以专用返工命令完全承接该动作。
- `TaskReadinessCoordinator` 已能处理任务进入 `todo` 后的 Sol 审核，以及 `ready → onReady` 的开发启动；应复用这条服务器门禁，不再创建第二套审核协调器。
- 当前 readiness 提示只映射用户评论。实现时必须显式注入当前返工单及来源引用，不能简单放开为读取所有 Agent 评论。
- 当前 `task_readiness_reviews` 以任务为主键保存最新审核。若同一任务经历多轮返工，返工单必须保留历史审核关联，不能只依赖最新 readiness 快照追溯。
- 发起返工必须验证任务仍为 `in_review`、未归档、版本匹配、当前没有并行发起中的返工命令。
- 命令需要幂等键、事务或等价原子保证、版本/CAS 保护和写后回读。
- 原子创建失败时保持 `in_review` 并保留草稿；返工单创建成功但 Sol 启动失败时，应持久化失败并进入 `blocked`，不得假装未发起或直接启动 Luna。
- 看板标识需要 Task API 返回当前有效返工轮次和状态摘要；只从评论文本推断不可靠。
- 任务状态、评论动作、readiness、AI 触发和调度规则变化时，必须同步更新 `docs/task-status-reference.md` 与 `docs/ai-intervention-triggers.md`，并保持 README 链接有效。
- 视觉规范来自 `web/src/styles.css`：Inter/PingFang 字体、现有主题变量、状态色、圆角、边框和阴影。
- 相关真实组件包括 `web/src/components/TaskDetail.tsx`、`web/src/components/TaskCard.tsx`、`server/task-readiness-coordinator.mjs`、`server/app.mjs` 和 `server/database.mjs`。

## 全状态要求

- 正常态：交付验收、AI 建议返工、返工审核中、返工待补充、返工开发中、返工结果待验收。
- 加载态：返工单/readiness 读取中，写动作禁用但任务正文可读。
- 空态：没有返工历史，仅在用户主动查看返工记录时出现。
- 搜索无结果：存在返工历史但筛选不匹配，提供清除搜索。
- 错误态：创建返工单失败、版本冲突、Sol 启动失败分别展示，不合并成通用错误。
- 部分可用：任务和返工单可读、AI 对话不可用时，只禁用对话入口。
- 只读态：任务归档后保留历史，禁止发起、补充和重新审核。
- 边界：长标题、两位数轮次、大量历史、附件上传中、评论编辑、重复点击、移动端和深色主题。

## Toast 规则

- 位置：桌面端右下角；移动端底部安全区上方。
- 成功：2.4 秒自动消失。
- 警告：4 秒自动消失。
- 错误：8 秒；存在明确恢复动作时提供按钮。
- 同时最多显示 3 条；新消息进入后按时间顺序堆叠。
- Toast 只说明已确认结果，不把“请求已发送”写成“审核已启动”或“开发已开始”。
