# 任务状态流程 — 需求总结

> 版本：v0.1
> 日期：2026-08-06
> 状态：设计探索完成，待 PRD

---

## 背景

任务详情当前使用原生下拉框平铺全部状态。这个控件能直接改值，但无法解释“进入待开发会触发需求审核”“审核中实际是开发后的交付验收”等业务含义，也把查看当前阶段与执行状态流转混在了同一个操作里。

用户希望状态像流程一样更容易理解和操作，同时明确允许跨阶段跳转。因此本设计采用“引导型流程”：系统突出推荐动作和状态影响，但不限制用户跳到任意合法阶段。

## 目标

本版本要解决的核心问题：

1. 第一眼看清任务当前处于哪个真实阶段、当前负责人是谁、下一步应该做什么。
2. 在允许跨阶段跳转的前提下，切换前清楚展示目标阶段会产生的实际影响。
3. 区分主流程、阻塞分支和终止状态，避免把“待解决”误解为固定的下一步。
4. 统一开发前“需求审核”和开发后“交付验收”的名称，消除“审核中”的歧义。

## 功能范围

### 做什么

- 将任务详情属性区的原生状态下拉框替换为“当前阶段卡”。
- 阶段卡显示动态阶段名称、当前负责人、阶段说明和推荐动作。
- 点击阶段卡打开纵向迷你流程弹层。
- 主流程展示：积压事项 → 待开发/需求审核 → 开发执行 → 交付验收 → 待复盘 → 完成。
- 异常区单独展示“待解决”和“已取消”。
- 所有合法状态都可选择，允许跨阶段跳转。
- 选择目标后先展示“从哪里切到哪里”和目标阶段影响，再确认提交。
- 需要文本输入的推荐动作跳转并聚焦评论区；只读动作打开关联对话；纯状态动作直接进入切换确认。
- 覆盖桌面端、窄屏、移动端、浅色和深色主题。
- 覆盖加载、保存、冲突、只读、搜索无结果、部分信息不可用等状态与 Toast 文案。

### 不做什么

- 不改变现有数据库状态枚举（原因：本轮目标是改进展示和操作，不迁移数据模型）。
- 不禁止跨阶段流转（原因：用户已明确允许跨阶段跳转）。
- 不重做整个任务详情页、看板列或任务右键菜单（原因：控制 V1 范围，只处理详情属性区的状态体验）。
- 不改变需求审核、Agent 调度、评论意图或 AI 对话的服务端业务规则（原因：状态入口只解释并调用现有路径）。
- 不自动推断通用“待解决”应返回的原阶段（原因：当前数据模型没有统一的 `blocked_from_status`）。
- 不增加状态历史分析、流程统计、自定义状态或自定义状态机（原因：属于后续产品能力）。

## 载体

现有 Taskboard 应用的任务详情页。

入口位于 `web/src/components/TaskDetail.tsx` 的右侧 `.issue-properties` 属性区，替换当前“状态”原生 `<select>`。桌面端沿用 320px 属性栏；移动端将弹层转换为底部抽屉。

## 关键决策

探索过程中确认的产品和设计决策，PRD 和开发阶段必须遵守：

| # | 决策 | 原因 |
|---|------|------|
| 1 | 采用“当前阶段卡 + 纵向流程弹层 + 分组状态说明”组合 | 默认界面简洁，需要时又能看到完整流程与状态影响 |
| 2 | 允许跨阶段跳转 | 用户已明确确认，流程只负责引导而不是强制约束 |
| 3 | 状态选择采用“选择目标 → 查看影响 → 确认切换” | 跨阶段仍然自由，但不会因状态副作用不透明而误操作 |
| 4 | `in_review` 的界面名称改为“交付验收” | 与开发前的“需求审核”明确区分 |
| 5 | `todo` 根据 readiness 上下文动态显示“需求审核中 / 待开发” | 数据状态不能完整表达用户实际经历的阶段 |
| 6 | readiness 等待补充时显示“等待你补充”，同时保留其“待解决”异常属性 | 用户需要先知道谁应行动，而不是只看到宽泛阻塞标签 |
| 7 | “待解决”和“已取消”不进入主流程轨道 | 一个是异常分支，一个是终止状态，都不是正常下一阶段 |
| 8 | 需要评论内容的动作只负责聚焦评论区，不在属性栏重复造输入框 | 避免出现两个评论入口和不同步的草稿 |
| 9 | 保留现有状态色、字体、圆角、阴影和深色主题变量 | 与当前 Linear 风格保持一致，降低实现与认知成本 |
| 10 | 移动端使用底部抽屉，不强行保留锚定弹层 | 320px 以下空间不足，底部抽屉更稳定且易操作 |

## 技术约束

- 合法状态来自 `shared/domain.mjs` 的 `TASK_STATUSES`；设计不能创造新的持久化状态值。
- 当前状态字段在 `web/src/components/TaskDetail.tsx` 中直接调用 `saveTask({ status })`。
- `todo` 对分配给 Codex 的任务会触发 `TaskReadinessCoordinator`，因此菜单必须明确提示“进入后启动需求审核”。
- `pending_retrospective` 在 SQLite 中映射为 `status='done' + retrospective_status='pending'`，界面必须统一显示为“待复盘”。
- `blocked` 同时承载审核等待、启动失败、执行失败和人工阻塞等含义；优先使用 readiness/intervention 信息生成具体说明，信息不足时只显示“待解决”。
- 当前模型没有通用 `blocked_from_status`、`previous_status` 或 `resume_status`，不能承诺一键“返回原阶段”。
- 任务更新使用版本号进行并发保护；`VERSION_CONFLICT` 必须刷新任务并提示用户重新确认目标阶段。
- 已归档任务只读，阶段卡与流程节点必须禁用。
- 视觉规范来自 `web/src/styles.css`：Inter/PingFang 字体、320px 属性栏、36px 属性行、`--accent: #5e6ad2` 及现有状态色变量。
