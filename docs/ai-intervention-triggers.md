# AI 介入与触发事件

本文是任务面板中 AI 介入方式的事实参考。它回答三个问题：什么事件会触发 AI、会启动哪种 AI、任务和评论会发生什么变化。

相关状态含义见 [任务状态说明](task-status-reference.md)。

## 快速结论

任务面板目前不是一条单一的 AI 流程，而是由需求审核、主任务编排、普通开发、交付协调、独立讨论、定时自动开发和故障恢复几套入口共同组成。

最常见的主流程是：

```text
任务进入待开发
  → Sol 只读需求审核
  → 信息不足：写入问题并转到待解决
  → 审核通过：
      普通任务或手动进入待开发的子任务 → 开发 worker（默认 Luna）
      顶层主任务                         → planner（默认 Sol）拆分子任务 → 开发 worker 执行
  → 开发交付
  → 审核中
  → 用户验收
    或提交返工意见 → 待开发 → Sol 返工审核 → 开发 worker 返工
```

## AI 角色与默认配置

| 用途 | 模型与强度 | 权限 | 说明 |
| --- | --- | --- | --- |
| 独立任务需求审核 | `gpt-5.6-sol`，`xhigh` | `read-only` | 判断需求是否足以开始开发 |
| 顶层主任务下的子任务派发审核 | 默认 `gpt-5.6-sol`，`max` | `read-only` | 结合父任务、同级任务和依赖判断是否允许启动开发 worker |
| 顶层主任务规划 | 默认 `gpt-5.6-sol`，`max` | `read-only` | 生成结构化子任务计划 |
| 任务开发 | 默认 `gpt-5.6-luna`，`max`，`priority` | `workspace-write` | 实现和验证任务 |
| 独立讨论或交付重新审核 | `gpt-5.6-sol`，`xhigh` | `read-only` | 不应修改产品文件或主动改变任务状态 |
| 项目自动开发 | 用户在项目菜单中选择 | 由 Codex 自动化执行环境决定 | 定时认领一个 `todo` 任务 |

任务绑定对话只锁定角色和沙箱权限：顶层且带有 `主任务` 标签的任务默认使用 planner/Sol，其余任务默认使用 worker/Luna。模型、推理强度和服务等级只是新对话默认值；对话空闲时用户可以修改，后续运行与故障恢复沿用该线程当前设置。既有线程不会在服务启动或任务运行前被批量改回默认值。配置来源见 [`server/ai-chat.mjs`](../server/ai-chat.mjs)。

## 触发事件总表

| 事件节点 | 附加条件 | AI 行为 | 可观察后果 |
| --- | --- | --- | --- |
| 使用 `idea-inbox` 或 `inbox-unclassified` 创建任务 | `Obsidian Vault` 项目存在 | 任务实际写入 `Obsidian Vault`，保留“灵感收件箱”或“待归类需求”来源标签，并移除 `主任务` 标签 | 默认作为普通任务，不会仅因来自收件入口而启动 planner 拆解；原项目 ID 继续作为兼容入口 |
| `task.created`、`task.moved` 或 `task.updated` 后状态为 `todo` | 负责人必须是 Codex Agent；不是已经批准的内部回写 | 启动 Sol 需求审核 | 详情中出现审核轮次和审核对话 |
| 待开发任务修改标题、描述或标签 | 负责人必须是 Codex Agent | 基于最新内容重新审核 | 正在运行的旧审核会因版本变化而重新开始 |
| 用户发布 `resume` 评论 | 当前审核为 `awaiting_input` 或 `failed` | 继续 Sol 需求审核 | 通过后回到待开发；否则继续待解决 |
| 需求审核返回 `ready` | 任务仍在待开发或待解决 | 普通任务启动开发 worker；顶层主任务进入 planner 编排 | 开始开发对话或主任务规划 |
| 顶层主任务规划完成 | 结构化计划有效 | 创建子任务并按依赖调度开发 worker | 子任务可能从积压事项直接进入进行中 |
| 编排中的 worker 运行结束 | 完成、失败或中断 | 服务器生成 handoff，唤醒父任务 planner | 完成转审核中；失败或中断转待解决 |
| 编排子任务被手动改为审核中、待解决或已取消 | 该任务属于主任务编排 | 生成状态 handoff，唤醒父任务 planner | planner 决定确认、补证据、继续开发、调整方案、创建修复任务或停止 |
| 点击“发布并开始开发” | 状态为待开发且需求审核已经 `ready` | 创建或复用任务绑定对话并启动开发 | 普通任务启动开发 worker；顶层主任务由服务器恢复 planner 编排 |
| 点击“提交返工并重新审核” | 状态为审核中，本地 AI 对话可用 | 将完整修改意见登记为返工轮次，移动到待开发 | Sol 审核本轮返工单；通过前不启动开发 worker |
| 点击 AI 审核评论中的“采纳意见并发起返工” | 状态为审核中，本地 AI 对话可用 | 复制 AI 反馈为一条用户返工评论并登记返工轮次，移动到待开发 | 与手写返工意见进入同一条 Sol 审核链路 |
| 点击“新开 Sol 对话” | 本地 AI 对话可用 | 创建独立 Sol X-High 只读对话 | 任务状态保持不变 |
| 审核中点击“发布并重新审核” | 本地 AI 对话可用 | 创建交付重新审核 Sol 对话 | 状态保持审核中；完成后新增一条 AI 审核评论 |
| AI 对话面板发送首轮或后续消息 | 已选择项目；新对话还需要可用工作区 | 在所选对话中启动一个 AI run | 对话变为运行中；是否改变任务取决于是否绑定任务及 Agent 是否执行任务板操作 |
| 用户中断正在运行的 AI | 对话存在运行中的 run | 终止当前进程并将 run 标记为 `interrupted` | 编排 worker 会生成失败 handoff 并把子任务转到待解决；普通独立 run 不自动改任务状态 |
| 在失败或中断的任务对话点击“继续处理” | 最新 run 属于仍在待解决的编排子任务，且对应 handoff 已结束协调 | 复用同一开发对话及其当前模型创建新的服务器托管 worker attempt | 子任务从待解决进入进行中；旧 run、dispatch 和 handoff 保持不变，本次终态会生成新 handoff |
| 项目自动开发的定时器到点 | 自动开发已启用，项目存在负责人为 Codex Agent 且 readiness 为 `ready` 的 `todo` | 选取一个任务，读取任务和评论后认领并开发 | 直接移动到进行中；完成后评论并移动到审核中 |
| 特定 AI 运行失败 | 错误为 `CODEX_JSONL_LINE_TOO_LARGE`，任务仍在进行中，且满足自动重试限制 | 延迟后继续同一任务对话 | 最多进行受限次数的自动恢复 |
| 服务启动 | 存在运行中的审核、编排、handoff 或重试任务 | 回读持久化状态并协调恢复 | 无法确认的旧运行会失败或重新排队，不会盲目重放 planner/worker |

## 需求审核的完整后果

需求审核由 [`TaskReadinessCoordinator`](../server/task-readiness-coordinator.mjs) 处理。

### 会启动审核的事件

- 新建任务时直接设置为 `todo`。
- 从其他状态拖动或修改到 `todo`。
- 在审核中提交手写返工意见，或采纳 AI 交付审核意见发起返工。
- 已在 `todo` 时修改标题、描述或标签。
- 审核等待补充或失败后，用户点击“发布并重新审核”。

以上入口都要求负责人是 Codex Agent。

### 不会单独启动审核的修改

- 修改优先级。
- 修改截止时间或重复设置。
- 修改开发分支或 worktree。
- 只修改负责人。把一个已经处于待开发的任务改派给 Codex Agent，本身不会触发审核。
- 编辑或删除旧评论。协调器只监听新建的 `resume` 评论。

### 审核结果

`ready`：

1. 写入一条包含结论、已确认项和开发假设的 Agent 评论。
2. 如果任务在待解决，则移回待开发。
3. 发出带有 `readinessApproved` 标记的内部 `task.moved` 事件。
4. 普通任务或手动派发的子任务启动开发 worker；顶层主任务启动 planner 编排。若该主任务已有失败编排，服务器按当前 readiness 轮次创建幂等 planner 重试 dispatch，并复用原 planner 线程继续运行。

如果任务带有当前返工轮次，Sol 会在任务上下文中收到该轮返工评论。该评论单独发送，不再同时重复出现在普通评论历史中。普通任务和父任务上下文只携带最近 20 条相关用户评论，每条最多 2,000 字符；独立 `discussion` 评论不进入 readiness。只有本轮审核返回 `ready` 后才会进入上述开发路线；旧交付和旧审核评论不会代替本轮返工单。

`needs_confirmation`：

1. 写入带 Q 编号的阻塞问题。
2. 将待开发任务移动到待解决。
3. 等待用户通过“发布并重新审核”明确继续。

审核运行失败：

1. 保存失败状态和错误。
2. 写入可见的失败评论。
3. 将待开发任务移动到待解决。

如果项目没有可用的本地工作区，AI 对话可能在审核记录创建前失败。此时应检查项目 `workspacePath`、任务的 `readinessReview`、AI 对话和服务日志，不能仅凭任务位于待开发就判断审核已经开始。

## 审核通过后的两条开发路线

### 普通任务和手动派发的子任务

审核通过后，服务器自动创建或复用任务绑定的开发对话；新对话默认 Luna，既有对话沿用用户当前选择。启动失败时，服务器写入失败评论并将任务转到待解决。

普通任务的运行没有主任务 dispatch。服务器负责启动开发 worker，但运行结束后的评论和状态推进依赖该开发对话按指令更新任务；它不会像编排子任务一样，仅凭运行终态自动生成 handoff。

### 顶层主任务

满足以下条件才按主任务处理：

- 带有 `主任务` 标签。
- 没有父任务。
- 状态为待开发。
- 需求审核已经通过。

planner 返回结构化子任务计划。服务器持久化计划、建立父子关系和依赖，再调度满足依赖的开发 worker。计划中的 `childKey` 如果精确匹配同项目、未归档、且已经属于该主任务的直接子任务，服务器会原位纳管该任务并保留其当前状态；否则创建新子任务。既有子任务处于审核中、待解决或已取消时，先生成状态 handoff 交给父任务 planner，再决定是否继续调度。依赖任务达到审核中或完成后，后续子任务才具备调度资格。审核通过事件和审核已通过后的新 `resume/development` 评论都可以恢复失败的 planner；两条路径分别使用 readiness 轮次或评论 ID 作为幂等 dispatch 键，不会盲目重放旧 run。

由 planner 新建的子任务从积压事项开始，但 worker 调度会直接将它们推进到进行中。原位纳管的既有子任务保留原状态。它们不会逐个走普通的 `todo → readiness` 路径；即使已有 readiness 通过记录，也只允许主任务 `TaskCoordinator` 启动服务器托管 worker，不再同时走普通任务的公开 turn 路径。父任务 planner 和 handoff Sol 构成这条路线的协调层。

服务启动恢复会逐个协调主任务：已处于审核中、待解决、完成或已取消的终态子任务不会再次检查或认领旧 worker dispatch；单个主任务的旧 dispatch 冲突会记录错误并跳过，不会阻断其他主任务继续恢复。若旧 worker dispatch 已失败，但子任务随后完成了新一轮父任务派发审核，服务器以审核轮次创建新的幂等 worker attempt，并复用原开发对话，不重放或改写旧 dispatch。历史 dispatch、handoff、评论和任务状态保持原样，不做自动回填或改写。

## Handoff：开发 worker 结束后 planner 如何接管

Handoff 是编排子任务向父任务 Sol 报告交付或阻塞的结构化记录。

编排 worker 完成时，服务器会：

1. 将子任务移动到审核中。
2. 保存开发 worker 的交付摘要。
3. 新增一条结构化 Agent 评论。
4. 将 handoff 放入父任务 FIFO 队列。
5. 唤醒父任务 Sol，按顺序处理。

Handoff 会携带最近一条非 handoff 评论的有限摘要；服务器不会把上一条结构化 handoff 评论再次嵌入下一条记录。发送给 planner 或后续 worker attempt 时只保留协调所需字段，交付或阻塞摘要最多 12,000 字符、最近评论最多 4,000 字符、错误最多 2,000 字符，避免历史快照和内部 ID 持续放大上下文。

完整 handoff 继续保存在专用表中，供审计和父任务协调使用。新生成的结构化评论只保留展示快照：不再重复写入 `summary`，交付或阻塞内容最多 12,000 字符，最近评论最多 8,000 字符；超长内容可回到原评论或绑定对话查看。任务详情顶部只展示一次完整验收内容，经历日志中的同一条主交付仅保留来源和时间；其他 handoff 仍显示中文“系统协调记录”。详情页会合并同一介入原因的多个筛选视图，但各视图筛选能力保持不变。旧评论不回填、不改写，继续按兼容显示逻辑读取。

worker 失败或中断时，服务器将子任务移动到待解决，并保存阻塞摘要。planner 可以返回的后续动作包括确认、继续、修订、要求补证据、创建修复任务或停止。继续、修订和补证据会在同一开发对话中创建新的 worker attempt，并沿用该对话当前模型。

如果 Sol 已经停止该 handoff，但用户仍决定继续，可以在绑定对话中点击“继续处理”。服务器会以失败或中断的 source run 作为幂等键，创建新的 worker attempt，并先把子任务从待解决移到进行中。这个入口不会把旧 handoff 从 `stopped` 改回待处理，也不会重写旧 solution；新 run 结束后会生成新的 handoff，供父任务 Sol 继续协调。若旧 handoff 仍在排队或处理中，服务器拒绝人工并行恢复。

Handoff 协调重试耗尽时，服务器仍保留结构化失败评论；经历日志将其显示为“系统协调异常”、重试次数和失败原因，不显示原始 JSON。

## 评论区三个按钮的区别

| 按钮 | 评论 intent/action | 是否触发 AI | 状态变化 |
| --- | --- | --- | --- |
| 仅发布 | `comment/comment` | 否 | 无 |
| 发布并重新审核 | `resume/review` | 只在需求审核等待补充或失败时继续 Sol | 审核通过后可能从待解决回待开发 |
| 发布并开始开发 | `resume/development` | 是 | 待开发任务启动或恢复开发 |
| 提交返工并重新审核 | `resume/review` + `reworkRound` | 是 | 审核中转待开发；Sol 通过后才启动开发 worker |
| 采纳意见并发起返工 | 新建用户 `resume/review` + `reworkRound` | 是 | AI 审核意见作为返工单进入同一条流程 |
| 新开 Sol 对话 | `discussion/discussion` | 是 | 无 |
| 审核中的发布并重新审核 | `discussion/review` | 是 | 保持审核中，完成后新增审核评论 |

“发布并重新审核”这个文案对应两条不同路线：待解决时是需求复审，审核中时是交付复核。判断后果时必须同时看当前任务状态。

任务存在当前 readiness、planner、worker、自动重试、handoff 或编排子任务活动时，当前责任已交给 Agent。任务卡按实际活动显示“Agent 审核中 / 规划中 / 执行中 / 协调中 / 重试中”或“子任务处理中”，并显示“当前无需你处理”；这些进度不进入三个“待我”介入视图。若当前 Agent 活动不早于历史 failed/stopped handoff，历史失败只保留为活动记录，不再生成当前人工介入原因。只有最新流程明确等待用户输入或失败且没有更新的 Agent 活动接管时，才恢复人工介入提示。仅有旧线程或旧 run 不算当前活动。该显示规则不回填或改写历史 handoff、评论和任务状态。

## 项目自动开发

项目标题旁的自动开发开关会创建或更新 Codex 定时自动化。间隔可选 5、10、15、30 或 60 分钟，模型和推理强度由用户选择。

每次运行只处理一个负责人为 Codex Agent 且 `readinessReview.status === "ready"` 的 `todo`。自动化提示只补充项目范围和 readiness 选择条件；读取任务/评论、版本化认领、绑定开发上下文和交付验收格式统一遵循 `manage-taskboard` Skill，避免两处重复维护。审核记录缺失、仍在运行、等待补充或失败时必须跳过，不能抢先认领返工审核中的任务。

## AI 对话面板的手动入口

在 AI 对话面板点击“新建对话”只创建对话记录，不会启动模型。用户发送首轮消息或在已有对话中发送后续消息时，服务器才创建 AI run 并启动 Codex。

- 未绑定任务的对话：用户可选择 planner/worker、模型、推理强度和沙箱；对话会收到当前项目上下文。
- 绑定任务的对话：服务器根据任务锁定角色与沙箱；模型、推理强度和速度只是默认值，空闲时用户可自由切换。顶层主任务默认 planner/Sol，其余任务默认 worker/Luna。
- 正在运行的同角色任务对话受到重复运行保护，不允许为同一任务并行启动另一个相同角色的 run。
- 用户中断普通任务或独立对话时，只结束当前 run，不会自动选择新的任务状态。
- 用户中断主任务编排中的 worker 时，服务器把该终态作为失败 handoff 处理，子任务进入待解决并唤醒父任务 planner。
- 失败或中断的普通对话仍可“重试上一条消息”。编排子任务显示“继续处理”，通过服务器创建新的 worker attempt，而不是把公开消息错误地绑定到旧 dispatch。

“在对话中打开”也不是 AI 触发器。它只在 Codex 原生输入框预填 `$manage-taskboard ISSUE-ID`；只有用户实际发送消息、Agent 读取并修改任务后，才会产生对话和任务板副作用。

### 模型默认值决策记录

- 背景：任务对话过去把模型作为角色锁定项，导致用户在模型菜单中无法切换，服务重启或新 run 还会把设置改回固定值。
- 决策：planner 新对话默认 Sol，worker 新对话默认 Luna；模型、推理强度和服务等级由线程持久化，用户选择优先。角色和沙箱继续由任务语义锁定。
- 历史边界：不批量迁移既有线程；已有线程保留当前模型，用户可以在空闲时手动切换。
- 回滚：恢复 `TASK_AI_LOCKED_SETTINGS` 和旧默认值即可；没有数据迁移或清理步骤。

## 独立 AI 对话的权限边界

“新开 Sol 对话”和“交付重新审核”创建的是未绑定 `issueId` 的 planner 对话。提示词要求只读讨论、不修改文件、不改变任务状态。

但服务器会向所有未绑定任务的对话自动注入 `manage-taskboard` Skill。因此“不改变任务状态”目前主要依靠对话提示约束，不是完全移除任务板写能力的硬隔离。相关逻辑见 [`server/ai-chat-process.mjs`](../server/ai-chat-process.mjs)。

## 不会自动触发 AI 的操作

- “仅发布”评论。
- 修改、删除评论。
- 添加或删除附件。
- 修改优先级、截止时间、重复设置或开发上下文。
- 普通任务直接移动到进行中、审核中、待复盘、完成或已取消。
- 只创建 AI 对话但不发送首轮消息。
- 点击“在对话中打开”但没有发送预填消息。
- 归档或恢复任务。归档会同步管理任务绑定对话的生命周期，但不会启动新的 AI 运行。

例外：主任务编排中的子任务被移动到审核中、待解决或已取消时，会生成 handoff 并唤醒父任务 Sol。

## 当前需要持续关注的行为

1. planner 自动创建的子任务会直接由开发 worker 调度，不逐个进入 readiness。
2. 普通任务审核通过后服务器已经自动启动开发 worker，但界面仍提供“发布并开始开发”，该按钮更像启动失败后的恢复入口。
3. “发布并重新审核”在待解决时是需求复审，在审核中时是独立交付复核；返工入口已经使用独立文案。
4. 未绑定任务的只读 Sol 对话仍会加载 `manage-taskboard` Skill。

这些是当前代码事实，不代表目标产品行为。修改其中任何一点时，应同时更新本文和 [任务状态说明](task-status-reference.md)。
