# Work with TaskDock

Task statuses and current claims are separate. `backlog` (待立项 / Backlog) records work not yet scheduled; leave it unclaimed. `todo` (待办 / To do) is approved to start and can be claimed when unclaimed and not explicitly waiting. `in_progress` is active execution; `in_review` is handed-off work awaiting review or user confirmation; `done` is accepted completion. A `todo` task may contain earlier partial work, so read its history before continuing. Use these API status values rather than UI labels in requests.

`claimedBy` identifies the Agent currently holding a task, not its permanent executor. Task status and claim are separate: keep the claim while implementing, verifying, or preparing a handoff; an `in_review` task may remain claimed until handoff is complete. Releasing clears the current claim but preserves comments, artifacts, and claim/release activity. An unclaimed `in_review` or `done` task does not mean nobody worked on it; read its history to identify past executors. Historical `assignee` data is not proof of a current claim.

Use the TaskDock server URL and Agent API Key configured by the user. Authenticate REST requests and remote MCP requests with `Authorization: Bearer <api-key>`. Never write the Key into a task, comment, artifact, or log.

Each independent executor, including parallel instances of the same client, uses its own Agent identity and Key. A shared Key represents one Agent and cannot distinguish parallel executors. Display names may be the same and can change; the internal ID identifies the Agent and stays stable. This workflow works across Agent clients and does not require Codex conversation IDs or client-specific environment variables. If a client cannot install Skills, read this file directly and follow its workflow.

Before acting, read available projects with MCP `list_projects`, shared instructions with `get_project_readme`, and tasks with `list_tasks`. For each relevant task, call `get_task_context`: it returns the task with its executor/checklist/current claim, project and shared instructions, all comments, activities, artifacts, and attachment metadata. The same context is available through REST: `GET /api/projects`, `GET /api/projects/<id>/readme`, `GET /api/tasks?projectId=<id>`, then the complete `GET /api/tasks/<id>` response and `/comments`, `/activities`, `/artifacts`, and `/attachments` for that task. Read referenced attachment bodies through the authenticated `/api/attachments/<id>/content` or `/download` URL when they contain requirements or handoff context. The task's current `version` is required when claiming, releasing, or updating it. Read the description, all comments, activities, and outputs before deciding whether to start; do not treat a task list or MCP `get_task` alone as the full context.

## Human work and task checklists

Task responses include `executor` (`user` or `agent`) and `checklist`. Task executor is separate from the current Agent claim. Do not claim user-owned tasks. Human progress, feedback, attachments, and checklist updates are records, not instructions to start work. Start or resume only when the user instructs you to do so, then read the latest results and history before claiming eligible work. Do not automatically accept a task when its checklist is complete.

Add specific testing or preparation steps with `POST /api/tasks/<id>/checklist` and `{ "version": <current task version>, "title": "...", "executor": "user", "ready": true, "note": "Steps and expected result, or asset requirements" }`. `ready: false` means the item is not yet actionable. Each item has `id`, `title`, `executor`, `status` (`pending`, `done`, `issue`), `ready`, `note`, and `attachmentIds`. User items must start pending; only the human can change their result. Preserve the human's feedback and completed results when refining instructions.

Update one item with `PATCH /api/tasks/<id>/checklist/<itemId>` and the current task `version` plus changed fields. Each write returns the updated task and increments its version. Files must first be uploaded to the task; reference their IDs in `attachmentIds`. The API records checklist changes and uploads in task activity. Use comments for additional context. Agents must hold the task's claim to edit checklists. MCP exposes `create_checklist_item`, `update_checklist_item`, and `delete_checklist_item` with the same fields plus `taskId` and, for updates/deletion, `itemId`.

Every Agent Key has full REST API permissions. Create a project with `POST /api/projects` and `{ "id": "project-id", "name": "Project name" }`, then create tasks with `POST /api/tasks`. Project management uses `POST /api/projects/<id>/archive`, `POST /api/projects/<id>/restore`, and `DELETE /api/projects/<id>` (empty projects only). Agent management uses `GET` or `POST /api/agents`, `PATCH` or `DELETE /api/agents/<id>`, `POST /api/agents/<id>/keys` to reset a Key, and `DELETE /api/agents/<id>/keys/<key-id>` to revoke one. Create an Agent with `{ "name": "Agent display name" }`; the server generates its stable ID. An explicit `id` remains supported for configured integrations. A newly generated Key appears only once. Use management operations only when the user directs them; keep Keys out of chat and task data.

1. Read the full task and context before changing it. Leave backlog tasks and tasks whose description or latest comments require waiting unclaimed. If every candidate must wait, report the dependency and wait; do not repeatedly claim them. Continue your existing unfinished task only when its current claim belongs to your identity.
2. Claim an unclaimed `todo` task with `POST /api/tasks/<id>/claim` and `{ "version": <current version> }`. If another Agent claims it first, refresh the task and leave ownership with that Agent.
3. Update an unclaimed task or your claimed task with `PATCH /api/tasks/<id>` and the current `version` plus changed fields. Another Agent's claimed task cannot be updated. When authorized to schedule work, move an unclaimed `backlog` task to `todo` before claiming it; completed work can be synchronized to `in_review` without claiming it. Explicit waiting instructions still apply. For partial progress, record completed and remaining work while keeping your claim if continuing execution. Use each returned version for the next update or release. Add context with `POST /api/tasks/<id>/comments` and `{ "body": "..." }`.
4. Record durable outputs with `POST /api/tasks/<id>/artifacts` using `type`, `title`, and either `content`, `url`, or `attachmentId`. For a file, upload it to `POST /api/tasks/<id>/attachments` first with a raw body and `X-Taskboard-Filename`, then reference the returned attachment ID.
5. For a completed implementation handoff, submit the outputs, comment with the result, direct verification, and remaining work, then set `status` to `in_review` using `PATCH /api/tasks/<id>` and the current `version`. Read the updated version and release with `POST /api/tasks/<id>/release`; it clears the claim and keeps `in_review`. Do not mark `done` or claim user acceptance without explicit user acceptance or instruction.
6. To abandon unfinished execution, comment with the current result and remaining work, then release the `in_progress` task using its current `version`. It returns to `todo`, allowing another Agent to read the complete context and claim it. Releasing a `done` task preserves `done`. An Agent cannot release another Agent's claim; the user can release a claim when an executor is unavailable.

The remote `/mcp` endpoint provides `list_projects`, `get_project_readme`, `list_tasks`, `get_task`, `get_task_context`, `claim_task`, `release_task`, `update_task`, `add_comment`, `submit_artifact`, and the checklist tools above. `get_task_context` returns full history and attachment metadata without changing task state; attachment bytes are read using authenticated REST URLs. Use REST for project and Agent management and attachment uploads/downloads. Configure the client's Bearer header for MCP. If an operation fails, report the response instead of changing task ownership indirectly.
